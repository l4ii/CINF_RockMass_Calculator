# 02_background
岩体分级首先是有规范依据的工程判断。GB/T 50218—2014《工程岩体分级标准》第一点零点二条明确，本标准适用于各类型岩石工程的岩体分级。第一点零点三条要求定性和定量结合，先确定岩体基本质量，再结合具体工程特点确定工程岩体级别。条文说明列举矿井、巷道、地下采场和露天矿，但条文说明与正文应区分效力。软件需要把这些判断过程与工程记录对应起来。查表、计算、誊录和编书包含重复操作，项目希望将这些环节组织在统一流程内；本次材料没有院内工时和项目量统计，因此没有使用“逐年增长”或具体效率百分比。

现行状态及二〇一五年五月一日实施日期核查于二〇二六年十月二十五日，来源为出版机构平台工标库，https://www.gongbiaoku.com/book/nx217214mw6?query=GB02 。条款依据来自标准原版扫描件，第三方托管地址为 https://www.diji99.cn/guifan/13.%E5%B7%A5%E7%A8%8B%E5%B2%A9%E4%BD%93%E5%88%86%E7%BA%A7%E6%A0%87%E5%87%86%20GBT50218-2014.pdf ，PDF第十三页及第四十六页。正式评审可替换为单位购买标准的同条款页。

# 03_landscape
项目定位需要建立在对既有工具的客观认识上。Rocscience现行RSData提供多类材料强度准则、GSI估参、多材料分析及Excel导出，不能概括为只能计算一种方法。强度准则也不等同于六种岩体分级体系。NGI已经提供二〇二五年修订的Q-system手册及App或PDF指南，手册列有数字测绘平台的应用，不能称国外仍全部手工。Excel表格可以按工程需求定制，其能力取决于具体实现。本项目将重点放在设计院工作流中的多方法组织、点位记录和报告交付；这属于本次材料的集成定位，不是穷尽市场后得出的首创结论。

RSData产品及技术规格依据为 https://www.rocscience.com/software/rsdata 与 https://www.rocscience.com/help/rsdata/overview/technical-specifications 。NGI公开说明见 https://www.ngi.no/en/research-and-consulting/infrastructure-container/tunnels-and-the-q-system/ 。二〇二五年四月手册见 https://prod.ngi.no/globalassets/bilder/forskning-og-radgivning/bygg-og-anlegg/q-handbook_2025_english_final.pdf ，数字测绘示例在印刷页第四十四至四十五页。Excel栏为项目工作流分析，不代表对某个具体商业表格的测试。

# 04_roadmap
总体技术路线包括经验知识化、智能辅助录入、多方法计算、依据记录和成果输出。它是研究方案，不表示五个环节均已达到同一成熟度。当前可以核查的软件底座是统一数据结构、各方法计算与项目点位交付。后续四个技术页分别讲清计算、管理与输出、本地助手、图像辅助判识。已有代码实现与后续验证分开陈述，尤其不能将带版本号的输入文件直接解释为已经具备不可变审计链。助手目前有文本调用链，模型部署和知识质量仍需验证；多模态当前属于拟开展路线。

依据为当前仓库frontend/src/types/rockmassCase.ts、frontend/src/methods及frontend/src/utils中的计算与文件管理代码，以及backend/assistant_api.py。技术路线为本汇报依据用户大纲进行的方案整理。

# 05_engine
第一项技术是多方法分级计算。界面集成RQD、BQ、Q、RMR、MRMR和GSI六种入口，共用工程、点位和方法输入字段。代码中有ClassificationAdapter接口，包括初始化、归一化、校验、计算和结果描述。RQD、BQ、Q、MRMR和GSI有适配器实现，RMR保留专用评分与汇总模块，因此结构图明确分开两条实现路径。通用界面注册表目前直接注册RQD、BQ和Q，其余方法有专用页面，不能说全部已统一为同一个调用入口。各方法实现评分表、边界处理和适用限制。点位记录methodId、standardId和inputVersion，导入时检查兼容性。当前读取按现有代码重算，没有历史算法执行器，因此“版本记录”与“历史原样复现”应区别。

接口与数据字段依据为frontend/src/methods/types.ts第四十八至五十八行、frontend/src/types/rockmassCase.ts第二十二至五十三行。具体适配器位于frontend/src/methods，RMR计算位于frontend/src/utils/rmrCalc.ts。导入契约见frontend/src/utils/rockmassCaseFile.ts。这里展示实现架构，不构成六方法全部外部规范一致性认证。

# 06_case_report
第二项技术解决工程记录与成果交付。案例管理工程名称、部位和备注，案例下维护多个点位，每个点位保留方法、标准、输入版本和参数。本页左侧是真实运行界面，六个点位全部使用虚构演示输入，不是现场工程数据。BQ与Q等方法保存原始输入和采用口径，例如Q的原始RQD与计算采用值可分别解释。软件支持本地项目文件及Word计算书导出，右侧为实际导出界面，本次已经点击原生导出获得计算书文件并校验DOCX包内容。Q和GSI的报告代码支持带点位的附图，但MRMR的参数细表仍待完善。当前环境缺少Word或LibreOffice排版引擎，所以没有伪造报告截图，也未验证计算书分页效果。

依据为frontend/src/types/rockmassCase.ts、frontend/src/utils/reportDocxTemplate.ts、frontend/src/utils/reportProfiles/qReport.ts和gsiReport.ts。MRMR导出边界见frontend/src/utils/classificationReportDocx.ts。截图与导出文件来自本次独立临时浏览器运行，输入和结果留存在rockmass_presentation_assets_20261025目录的demo-inputs-and-results.json。

# 07_local_assistant
第三项技术为本地经验知识助手。当前后端具有llama.cpp加载本机GGUF模型和进程内推理的调用链。方法知识以本机md或txt片段读取并拼接到提示词中，同时注入当前页面快照与对话上下文。这个实现是文本知识注入，不等于向量检索系统，也不是训练了新模型。预期服务范围是方法选择、参数含义和取值依据查找，最终采用值仍由工程师确认。本页保留了需要实测的SRF问题，而没有编造模型回答。当前工作区没有GGUF模型文件，知识内容也需要清理过时条目并经专家审核。设备绑定的离线授权有独立实现，但软件更新存在联网路径，不能将本地推理等同于整个软件绝不联网。

代码依据为backend/assistant_api.py第五百六十三至六百一十行的加载、六百二十一至六百五十六行的知识文本读取、八百五十四至八百六十四行的上下文与九百三十四至九百六十四行的推理。页面数据见AssistantPanel.tsx；离线授权见electron/license.js；更新路径见electron/main.js。真实问答截图需要配置模型并完成一次可复查的问答后补入。

# 08_multimodal
第四项技术是拟开展的多模态辅助判识。当前仓库只有文本助手接口，尚未找到图像上传和视觉模型处理链路，因此没有标注为已经验证，也没有给出虚构识别框。研究方案由图像采集、特征识别、候选值建议和工程师确认组成。采集阶段需要拍摄尺度、图像质量和工程位置，识别结果应保留来源并给出可核查标记。后续需要统一标注规则、建立样本集，先做独立样本验证，再开展现场校准。图像能辅助描述结构面和岩块，但不能凭一张照片决定全部分级参数，岩石强度、水和应力条件仍需专项资料。

成熟度依据为当前代码接口检查，路线来自用户提出的后续研究方向。这里没有宣称已有样本库、技术路线验证完成、识别准确率或工程部署结果。

# 10_verification
本次验证有两类直接证据。首先实际运行了BQ、Q、GSI和MRMR四个域逻辑测试文件，七十九项测试全部通过，进程退出码为零。其次用三组合成输入直接调用计算函数，并以独立写出的基本算式断言结果。BQ取Rc五十兆帕、Kv零点五，结果三百七十五；Q取RQD八十、Jn四、Jr三、Ja一、Jw一和SRF一，结果六十；GSI采用JCond89二十五及RQD八十，结果七十七点五。三项软件值与人工期望均一致。它们用于内部回归和简单公式校核，不是规范书上逐字引用的算例，更不是第三方认证。真实工程、效率对比、Win7实机、本地模型以及完整六方法验收仍需补证。

实际命令为npm.cmd --prefix frontend test -- src/bq.methods.test.ts src/q.methods.test.ts src/gsi.methods.test.ts src/mrmr.strict.test.ts，二〇二六年十月二十五日执行，四文件与七十九项通过。证据保存在sources/rockmass_test_evidence_20261025.md。公式实现分别见frontend/src/methods/bq.ts第八百一十二行附近、q.ts第九百九十二行附近及gsi.ts第一千零五行附近。

# 11_institute_effects
设计院侧效果采用可执行的试点评价口径，当前没有真实基线时不补造百分比。工时按同一批点位、同一输出要求，对比人工和软件的计算加编书时间，记录分钟每点位，预期减少查表誊录，降幅等待测量。复核维度检查输入、采用值、方法和工程条件是否能对应查询，按依据齐全点位数除以抽检点位数统计完整率。同时说明，现有记录还不等同于不可变审签链。知识维度先统计经过专家审核的条目、版本和引用记录，以判断能否形成可维护的院内数字资料。后续试点应保留原始记录，避免把预计收益当成已实现成效。

本页为根据当前功能拟定的测量方案，不是实测结果。不得将本页转换为已节省工时、准确率或知识复用收益的数值声明。

# 12_application
工程侧首先是让参数与结果能够对应复核。多方法交叉核查可以帮助发现结果差异，但差异需结合方法适用条件和现场资料由工程师解释，不能直接宣称已经测得误判风险降低。软件记录可为设计审查提供资料，专项论证、审签与责任制度仍需独立建立。产品目前已有Windows安装包与设备绑定离线授权实现。矿山、隧道与边坡场景应分别核对具体方法和工况，特别是特殊边坡仍需专门论证。建议先完成院内试点，形成样板成果，再对旧系统、模型、知识条目和报告格式进行版本验收，之后组织院内外推广。

安装包与授权依据为release目录和electron/license.js。工程边界见GB/T 50218—2014第一点零点三、第一点零点四及第五点三点四条，标准扫描来源同背景页。Q支护需结合跨度及ESR，依据NGI二〇二五年手册第二十八至二十九页，https://prod.ngi.no/globalassets/bilder/forskning-og-radgivning/bygg-og-anlegg/q-handbook_2025_english_final.pdf 。推广顺序为本汇报建议。
